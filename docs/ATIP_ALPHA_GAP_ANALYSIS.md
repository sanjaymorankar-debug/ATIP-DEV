## Where ATIP already stands up

- **Backtesting, walk-forward, Monte Carlo and overfitting protection** — strategy/backtest_history.py (196 lines) is the only honest measurement instrument ATIP has. It replays REAL prices_daily bars (:44-48), holds entry rule, stop, holding window and costs identical across three exit policies so only the exit varies (:113-118), charges cost on every leg (no free extra leg for the two-exit policy), resolves same-bar stop/target ambiguity against the strategy (backtest_aggressive.py:144-151), and derives both ATR (:51-70) and the checkpoint momentum reading (:73-92) strictly from pre-entry bars — the one piece of genuine anti-leakage discipline in the codebase, and it is explicitly commented as such. It is also the only backtest that has actually changed a production parameter on evidence: strategy/aggressive.py:57-66 records trail_atr_mult moving 2.0 -> 4.0 because expectancy rose from -0.31% to -0.06% to +0.12% per trade across the tested multipliers. Critically, it shares the exact decision functions with live trading — strategy/live.py:193 ("Order matters and mirrors the backtest exactly") and both import checkpoint_decision/ratchet/trail_distance_pct/realised_pnl from strategy/aggressive.py — so measured behaviour and live behaviour cannot silently diverge. That shared pure-decision core is the asset every capability below should be built on top of.
- **Dashboard, API, documentation and tests** — A single-file dashboard that genuinely covers the daily workflow — market health, global markets, FII/DII, sector rotation, scores, Top 25 lists, portfolio, orders, signal history with outcome tracking — rendered server-side with an inline JS syntax check (_check_js) so a broken script cannot silently disable every tab.
- **Data platform and data quality** — Daily OHLCV depth plus the EOD coverage gate. prices_daily holds 234,311 rows over 426 distinct dates back to 2025-01-27 with a real UNIQUE(symbol,date) constraint and 0 duplicate keys, and pipeline/scheduler.py:108-145 will refuse to score a session whose bars are missing — the only quality control in the system with genuine test coverage (5 passing tests in tests/test_signal_pipeline.py, plus test_stale_days_measures_age and the IST date-shift and session-window tests). Freshness is likewise real and surfaced: dashboard/server.py:153 data_freshness() and the morning-brief STALE banner at alerts/telegram.py:241-248.
- **Decision engine, no-trade filter, explainability and strategy lifecycle** — A composite decision actually drives the system: ACS and the ATIP master score combine nine components with database-driven weights (weight_config, 105 rows), and determine_signal applies explicit regime and CRI gates rather than a single threshold.
- **Execution engine, microstructure and execution quality** — A real order lifecycle with an audit trail and a genuinely careful live/paper separation: orders/environment.py requires broker_env=LIVE *and* an explicit confirm before a real order can be placed, and orders/broker.py checks funds before every BUY and writes every attempt to order_log.
- **Factor research and validation** — The forward-outcome measurement plumbing in D:\Projects\ATIP\scores\signal_log.py. evaluate_outcomes() (line 360) walks forward from each signal, records hit/MFE/MAE/sessions_to_hit per threshold, is idempotent and resumable, distinguishes still_open from resolved, and treats a resolution reached across a data gap as PROVISIONAL (data_gap_sessions) so it can be revised once history backfills. success_report() (line 486) uses every signal watched for at least one forward session as the denominator, with the correction documented in its own docstring (95.2%/78.6%/60.0% reported vs 52.6%/28.9%/15.8% actual at the 3/6/8% targets). It is rigorous about look-ahead and honest about what it cannot measure (timing_unmeasurable, hits_gapped, not_yet_watched) — which is the hard part of factor validation. It is the right engine pointed at the wrong object: composite signals, not factors.
- **Feature engineering and the factor library** — The per-symbol indicator computation in D:\Projects\ATIP\data\technical.py. `_step()` (technical.py:106-127) isolates each indicator so one broken library call costs one column instead of cascading; `_numeric()` (technical.py:129-148) fixes the object-dtype bug that killed ADX; the upsert refreshes all 37 fields on conflict (technical.py:367-370) so a re-run repairs old NULLs; and the Technical Score weights are read from weight_config (`_tech_weights`, technical.py:312-337 — 12 TS rows summing to 1.0, verified by query). Result: for the 11 dates from 2026-07-30 onward, 33 of 37 written fields are 100% populated across 503 symbols (5,533 of 7,164 rows; per-date query shows 503/503 non-null adx_14 on every date since 2026-09-07). That is a working, self-diagnosing indicator pipeline — it is just not yet a factor library.
- **Monitoring, safety and security** — Live trading is off by default and hard to turn on by accident: broker_env defaults to PAPER, an unrecognised value falls back to PAPER with a warning (orders/environment.py:51), and a real order additionally requires confirm=True (orders/broker.py:181). Every order attempt, success or failure, is written to order_log, and every pipeline job to pipeline_log (928 rows).
- **Regime engine and machine learning** — The outcome-measurement plumbing in scores/signal_log.py. evaluate_outcomes (lines 359-470) is genuinely careful forward-looking measurement: it reads bars strictly with `date>?`, records MFE/MAE per threshold, is idempotent and resumable, marks a resolution reached across a data gap as provisional and re-checks it (`still_open=0 AND COALESCE(data_gap_sessions,0)=0` at lines 393-396), excludes gapped signals from timing statistics while still counting their hit/miss, and refuses to invent a 0.0 MFE for a signal with no forward bar yet. success_report (lines 484-582) now uses every signal watched for at least one forward session as the denominator, with `not_yet_watched` reported separately — the fix that moved the 3% hit rate from 95.2% to 52.6%, and it is regression-tested (tests/test_signal_pipeline.py:452, passes). Alongside it, the model_version/weights_hash stamping at scores/signal_log.py:263 and the git-commit + weight-set-hash helpers at lines 109-126 are the right provenance primitive. This is the foundation any ML validation would be built on: the label generation is already honest about what it does and does not know. What is missing above it is metrics, not measurement.

Runner-up: scores/engine.py:359-378, a measured, evidence-cited comment block explaining why the BUY gates are unreachable and explicitly forbidding lowering them to manufacture signals. That is the discipline a promotion gate would formalise.
- **Risk engine and portfolio construction** — A Portfolio Health Score that actually runs daily (scores/portfolio_health.py, 8 holdings scored 54.01 FAIR, portfolio beta 0.746 in tonight's log) and CRI as a per-stock crash-risk index inside the scoring engine.

## The biggest gap per domain

- **Backtesting, walk-forward, Monte Carlo and overfitting protection** — There is no dated portfolio equity curve anywhere in ATIP, and that single missing primitive blocks nine of the capabilities above at once. The Trade dataclass (strategy/backtest_aggressive.py:46-60) has no date field — only bars_held — and scores/backtest.py appends bare floats to res["rets"] (:218) while discarding entry dates (:246, `del res["entry_dates"]`). No backtest can therefore say WHEN a rupee was made. Consequences, all verified: CAGR, Sharpe, Sortino, Calmar, turnover and tail risk are uncomputable and score 0 grep hits repo-wide; Monte Carlo resampling and risk of ruin have nothing dated to resample; walk-forward has no time axis to roll along. Worse, the one drawdown figure ATIP does report is wrong: strategy/backtest_history.py:122-145 appends trades symbol-major (outer loop over symbols, inner loop over entry dates), and strategy/backtest_aggressive.py:206-210 then builds its equity curve in that list order — so "max_drawdown" is the drawdown of an alphabetically-ordered sequence of closed trades, not of an equity curve through time. Adding an entry_date to Trade and sorting chronologically is a sub-day change that unblocks roughly half this domain; it should be done before anything else here is built.
- **Dashboard, API, documentation and tests** — No documentation exists beyond a README and patch notes, the 15 API routes are unversioned and unauthenticated, and five substantial modules have no tests at all — including orders/rules.py at 945 lines, which is the code that places orders.
- **Data platform and data quality** — There is no data-validation layer and no DataQualityScore — nothing in the codebase ever asks whether a stored value is right, only whether a row exists and how old it is. The database proves the cost: 280 prices_daily rows violate low<=close<=high, 304 single-day closes move more than 25% with no corporate-action record (HEG 179.63 → 572.30 → 204.33 across 2026-03-25/26/27, the middle two sharing an identical volume), adj_close is NULL in 234,311/234,311 rows, index_levels carries 2,191 duplicate (date,time) pairs and 30,706 out-of-session rows, and 2026-09-14 has 503 technical_indicators rows and 501 ai_scores rows against 0 price bars. Every one of those is a single SELECT away from being detectable, and nothing runs it. The second-order effect is that declared inputs are silently constants: breadth/advance-decline = 25.93 and PCR = 61.54 on every single day, together carrying 0.25 of weight across MH and MSI, because scores/engine.py:18-23 renormalises around absent components without ever reporting that they were absent.
- **Decision engine, no-trade filter, explainability and strategy lifecycle** — The decision has one usable output state. Across 6,637 scored rows the only signals ever emitted are HOLD (4,493), WAIT (3,096) and BUY (52) — SELL has never fired once, and there is no NO-TRADE state carrying a reason, no strategy lifecycle, and no strategy health or factor decay monitoring.
- **Execution engine, microstructure and execution quality** — Nothing about execution is measured. No spread, no depth, no bid/ask is stored at all, slippage exists only as a paper-fill assumption rather than a measurement, and there is no implementation shortfall, fill rate, rejection rate or latency anywhere.
- **Factor research and validation** — No factor values are ever persisted, so there is no panel on which any IC statistic could be computed. The 105 sub-components are built into a local dict inside compute_vpi/compute_mri/compute_rri/compute_cri/compute_zpi/compute_ins/compute_acs (scores/engine.py:225-305) and thrown away; only the 9 composites reach ai_scores. Every capability in this domain — IC and its moments, IC decay and half-life, stability, the correlation matrix, regime-conditional IC — requires a (date, symbol, factor, value) panel joined to forward returns, and that panel does not exist. The secondary constraint is sample size: ai_scores holds only 17 distinct scored dates (2026-07-25 … 2026-09-18, with gaps), which is below the 30-day floor scores/backtest.py:290-294 itself refuses to draw conclusions under, and spi/fund_score are NULL in 7,641 of 7,641 rows. Persisting the component values costs little and is the unlock for nine of the ten capabilities; the date count then accrues on its own.
- **Feature engineering and the factor library** — There is no factor panel and no normalization contract. (a) `compute_indicators()` computes full pandas series but writes only `.iloc[-1]` (technical.py:159-249), so despite prices_daily holding 231,544 rows over 20 months, technical_indicators has only 16 distinct dates — and 5 of those (2026-07-25, 07-27, 07-28, 07-29, 08-03, 1,631 rows) are entirely NULL from adx_14 onward, leaving 11 usable factor dates. Nothing can be z-scored over time, ranked historically, or measured for information coefficient. (b) Every factor-to-score mapping is re-implemented ad hoc at the point of use: rsi_14 has 6 independent mappings, volume_ratio has 7, atr_pct is multiplied by 10, 12, 12 and 15 in four places. There is no single place where a factor is defined, so there is no place to attach a normalization, a lookback, or a version.
- **Monitoring, safety and security** — There is no kill switch of any kind and no pre-trade risk limit beyond a funds check — no daily loss limit, position cap, exposure cap, order-value cap, order-count cap, drawdown halt, sector cap or leverage limit. Separately, the dashboard serves unauthenticated order-placing POST routes on 0.0.0.0.
- **Regime engine and machine learning** — There is no machine learning in ATIP at all, and the regime label that everything else leans on is not a regime model — it is a five-way threshold on one hand-weighted sentiment average, 15% of which is a frozen constant.

Both halves are evidenced rather than inferred. On ML: grep for sklearn|scikit|torch|tensorflow|xgboost|lightgbm|catboost|statsmodels|hmmlearn|GaussianMixture|KMeans|RandomForest|LogisticRegression across every .py, .txt, .md and .json in D:\Projects\ATIP returns exit code 1 — zero matches. requirements.txt and setup.py list no ML or statistics package. No model artifact of any kind exists on disk. `git log --oneline --all` filtered for ml|model|regime|cluster|hmm|gmm|learn|train returns nothing across the entire history. The only fitted parameter anywhere is a univariate beta at data/technical.py:99. The one feedback loop that does exist — realised 5-day accuracy flowing into ACS at scores/engine.py:341 — has no date predicate, so re-scoring an earlier session reads outcomes dated after it. On the regime: scores/engine.py:318 is the whole classifier; the frozen 25.93 Breadth/AdvanceDecline pair (engine.py:315-316, fii_dii_market.adv_decline NULL in all 6 rows) caps mh_score at 88.89; three of the 17 stored sessions ran on defaulted index inputs because get_idx keys on `date=?` and index_levels has 14 dates; FII/DII were carried unchanged for 7 straight sessions because get_fii uses `date<=?`; and compute_mh has no unit test.

The binding constraint, however, is not the absence of libraries — it is that the data to fit anything on does not exist yet. market_health has 17 rows against 426 trading sessions (4.0%), of which only three of five labels have ever occurred (NEUTRAL 12 / BULL 3 / BEAR 2). technical_indicators — the feature table — spans 16 distinct dates against those 426 sessions, with 4 of its 41 columns NULL in every row. signal_log holds 67 rows, every one a BUY, 66 of them NEUTRAL. Any classifier trained on that would be fitting noise, and no validation metric would reveal it because none exists: no confusion matrix, no precision or recall, no ROC-AUC, no Brier score, no reliability curve, and no train/test split of any kind (`grep -iE "train_test|TimeSeriesSplit|cross_val|purged|embargo|holdout"` → no matches, so every swept threshold in the system is in-sample). And nothing would stop a bad fit from going live: weight_config has no UPDATE path in the codebase, meaning weights can only be changed by editing the SQLite file directly, and the next scheduled run at pipeline/scheduler.py:528 would use them that evening with no validation — the weights_hash that would record the change (scores/signal_log.py:120-126) has held the single value '29a27daf0548' on all 67 rows and has therefore never once detected anything.

Sequenced correctly, the cheap work comes first and none of it requires a new dependency: bound the ACS feedback query by date to stop the leak (one line, scores/engine.py:341); backfill regime history off the prices_daily 'NIFTY50' series, which already holds 425 sessions from 2025-01-27 and is the one deep, clean series in the database; backfill technical_indicators over that same span so features are 426 days deep instead of 16; then extend the existing success_report bucketing (scores/signal_log.py:522-527, currently keyed only on signal and threshold) by regime and ACS decile to get a confusion matrix and a first reliability table out of data already stored. Only after those does fitting anything become a question that data can answer.
- **Risk engine and portfolio construction** — There is no portfolio risk mathematics at all: no covariance matrix, no VaR, no Expected Shortfall, no optimiser, and no portfolio-level exposure limit that could stop an order. The one risk-based position sizing calculation that exists is never read by the order path.
