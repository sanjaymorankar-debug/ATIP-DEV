# Moving ATIP from SQLite to PostgreSQL (DBS-05)

**PostgreSQL is ATIP's final server database** (plan decision, 2026-10-09). MySQL / MariaDB is no longer supported: the MySQL backend (`db/mysql.py`), `tools/sqlite_to_mysql.py`, `tools/export_mysql.py`, `db/sql/atip_schema.mysql.sql` and the `mysql` compose profile were removed, and a `mysql://` URL is refused with a message pointing here. A deployment still configured for the MySQL runtime refuses to start rather than silently falling back to SQLite.

ATIP runs on SQLite (WAL) and **keeps doing so by default** until the runtime switch below is made. W38 added everything needed to move to PostgreSQL in steps, and proved it on a copy of the live database.

## What exists

| Piece | Purpose |
|---|---|
| `db/postgres.py` | `translate()` converts ATIP's SQLite SQL to PostgreSQL. `ddl()` converts CREATE statements. `trigger_ddl()` handles the append-only guards. `PgConnection` gives a sqlite3-shaped connection over psycopg 3. |
| `db/dialect_scan.py` | Scans every SQL statement in the code (via the AST) and lists what does not translate automatically. |
| `tools/sqlite_to_postgres.py` | Migrates a **copy** of the database: upgrade it to the release schema, translate the schema, copy the data, reset identity sequences, then verify row counts per table. |
| `db/sql/atip_schema.postgresql.sql` | A fresh, empty PostgreSQL database (all tables, indexes, append-only triggers, seed rows). Generated by `tools/schema_sql.py` through the same `plan()` as the migration tool; `tests/test_schema_sql.py` keeps it in step with the code. |
| `docker-compose.yml` `postgres` profile | PostgreSQL 16 for a single host: `docker compose --profile postgres up -d`. |
| `db/schema.pg_runtime_url()` | The opt-in runtime switch (below). |

## What `translate()` handles

- `?` placeholders become `%s`, and every `%` is doubled for psycopg.
- `INSERT OR IGNORE` becomes `ON CONFLICT DO NOTHING`.
- `INSERT OR REPLACE` becomes an upsert on the unique key that the inserted columns cover. SQLite replaces on any unique key, so the surrogate `id` is not used when it isn't inserted.
- `ON CONFLICT … DO UPDATE SET a=a+excluded.a`: the bare `a` is qualified with the table name. PostgreSQL rejects it as ambiguous otherwise.
- `date(x, '-N days')` and `date('now')`.
- `GROUP_CONCAT`, `IFNULL`.
- 2-argument `MAX` / `MIN` become `GREATEST` / `LEAST`.
- `LIKE` becomes `ILIKE`, because SQLite's LIKE is case-insensitive.
- `SUM(<comparison>)` gets a cast to int, because SQLite booleans are 0 and 1.
- `rowid` on `perf_ledger` / `ml_dl_benefit` becomes their identity `seq` column (`db.backend.ENTRY_ORDER_TABLES`). Any other `rowid` used as an ORDER BY tie-breaker becomes `ctid`, which is only valid on append-only tables.
- `BEGIN IMMEDIATE` takes a transaction-scoped advisory lock (one writer at a time, as in SQLite); `COMMIT` / `ROLLBACK` go through the connection.
- `CREATE TRIGGER IF NOT EXISTS` becomes `CREATE OR REPLACE TRIGGER`. `DROP TRIGGER name` gets its `ON table` from the catalogue.
- `PRAGMA query_only = ON` makes the following transactions `READ ONLY` (the MCP tools rely on this).
- `cursor.lastrowid` is read with `lastval()`.
- `sqlite_master` and `PRAGMA table_info` are answered from `information_schema`.
- The connection PRAGMAs become no-ops.

Anything else raises `UnsupportedSQL` and names the construct. A missed query fails loudly rather than returning different data.

**Status (2026-10-10):**
- 1,648 statements; 1,647 (99.9 %) translate automatically.
- The one that doesn't is the one-off SQLite repair `tools/repair_news_timezone.py` (`strftime()`).
- (W38 measured 1,327 statements at 99.7 %.)

## What the connection does beyond translating

`PgConnection` makes PostgreSQL behave the way ATIP's SQLite code expects:

- **Session time zone pinned to UTC.** SQLite's `CURRENT_TIMESTAMP` and `date('now')` are UTC. A PostgreSQL server installed from packages runs in the OS zone (IST), so without the pin, defaulted timestamps were 5h30m off.
- **A failed statement fails alone.** PostgreSQL normally aborts the whole transaction. Inside a write transaction each statement now runs in a savepoint; a failed read outside one rolls back a transaction that has written nothing. Without this, a "is the table there yet?" probe after a write threw the write away at the next commit.
- **Entry order.** New `perf_ledger` / `ml_dl_benefit` tables get `seq`. One made by an earlier release gains the column on the next start; rows are numbered in physical order, which on these append-only tables is the order they were written. `tools/sqlite_to_postgres.py` copies them in rowid order.

Run `python -m db.dialect_scan --details` to see the current list.

## Verified (2026-10-10, native build)

On a throwaway PostgreSQL 16, a database built from nothing with `init_db()` + `seed_weights()` + `ops.migrations.apply()`, with the runtime switched over the normal way:
- Migrations 0001-0006 all apply, a second run finds nothing pending, and `ops.migrations.validate()` is clean. Before this, every migration failed at `BEGIN IMMEDIATE`, so a database built this way had no append-only guards and lacked the migrations' indexes.
- Its tables, columns, indexes and the 16 append-only triggers are identical to `db/sql/atip_schema.postgresql.sql` loaded into an empty database (the file additionally holds the tables the order / paper / signal / strategy / recovery modules create on first use).
- On the loaded file: `ops.jobs.acquire()`, `ml.deep.allowed_to_activate()`, `cursor.lastrowid` and `PRAGMA query_only` work, and the append-only guards fire.
- `tests/test_postgres_backend.py` runs live in CI against a PostgreSQL 16 service.

## Verified (2026-10-02)

The test used a throwaway PostgreSQL 16 and a copy of the live database:
- 213 tables and 497,317 rows copied; the row counts are identical table by table.
- All 198 GET API routes ran on PostgreSQL with **0 server errors**. 31 returned 503 because enterprise features are off.
- Upserts, alert dedupe, the job-health check, the append-only triggers and the catalog queries were also exercised.

The same test found a W36 bug that also affected SQLite (the quant factor set). It is fixed.

## Migrating

1. **Take a copy.** For example `python -m ops backup`, then use the backup file. The tool refuses the live database.
2. **Dry run:**
   `python tools/sqlite_to_postgres.py --source <copy.db> --out atip_data/pg_migration`
   It writes `schema.postgresql.sql` and `plan.json`.
3. **Copy and verify:**
   `pip install "psycopg[binary]"`, then
   `python tools/sqlite_to_postgres.py --source <copy.db> --target postgresql://user@host:5432/atip --execute`
   Or, for a new installation with no data, load `db/sql/atip_schema.postgresql.sql` into an empty database instead of steps 2-3.
4. **Switch the runtime (experimental).** All three are required:
   - `ATIP_DATABASE_URL=postgresql://…`, read from the environment, else the project's `.env`, else the file `atip_data/secrets/ATIP_DATABASE_URL` (both git-ignored).
     - This must be the ATIP-specific variable. A generic `DATABASE_URL` left by another project is ignored on purpose; validation warns that it is.
   - In `config.json`:
     - `"database": {"backend": "postgresql", "allow_experimental": true}`
   - Validation (the start-up report) names whichever of the three is missing. In `production` that stops start-up rather than letting ATIP run on the SQLite file.
5. **Watch the first days.** `/compliance`, `/api/platform/postgres` and the job-health panel.

## Neon

ATIP's hosted PostgreSQL is Neon. One Neon project; on every branch the database is
`bk_atip`, owned by the login `bk_atip_app` (the bkesari naming scheme).

| Neon branch | Used by |
|---|---|
| `production` | the owner's Mac, whose snapshot bkesari.com shows (and `bkesari.com/ATIP/` if that is ever hosted) |
| `test` | `test.bkesari.com/ATIP/` |
| `dev` | `dev.bkesari.com/ATIP/` |

Each machine's `.env` holds only its own tier's URL.

**Which URL.** In the Neon console: the branch → **Connect** → role `bk_atip_app`, database
`bk_atip`, **Connection pooling off**. That is the direct endpoint: its host has no
`-pooler`. ATIP is one long-lived process that runs its own migrations at start-up, so it
uses the direct endpoint. Keep the string exactly as Neon shows it:

```
ATIP_DATABASE_URL=postgresql://bk_atip_app:<password>@ep-<id>.<region>.aws.neon.tech/bk_atip?sslmode=require&channel_binding=require
```

Neon's integrations also write `DATABASE_URL` (pooled) and `DATABASE_URL_UNPOOLED`
(direct) for other projects. ATIP reads neither: copy the direct one into `ATIP_DATABASE_URL`.

What was checked against a local stand-in (TLS PostgreSQL 16 and a PgBouncer in
transaction mode; `tests/test_neon_parity.py`, `TEST_SPEC.md` level S7):

- **TLS.** The URL reaches libpq unchanged, so `sslmode=require` and `channel_binding=require` both apply. The connection only adds its UTC time zone (`options=-c TimeZone=UTC`).
- **Scale to zero.** A suspended compute drops idle connections. ATIP opens a connection per call (`db.schema.get_connection`), so the next call simply reconnects. A connection held across the drop raises `sqlite3.OperationalError`, which ATIP's callers already handle. The first connection after a suspend is slower; psycopg waits up to 130 s by default.
- **No superuser.** `main.py --init` and the migrations run as the owning role, and ATIP needs no extension.
- **The pooler**, if ATIP is ever pointed at it, works: the only locks are transaction-scoped (`BEGIN IMMEDIATE` becomes `pg_advisory_xact_lock`), psycopg's automatic prepared statements rely on the pooler's protocol-level support (Neon's has it), the time zone travels as a startup option, and a connection rolls back its open read before closing, so the pooler can reuse the server connection. Run `--init` and the migrations over the direct URL all the same. The local PgBouncer cannot do channel binding, so through it the checks use `sslmode=require` alone; Neon's pooler accepts the full string.

### Moving the Mac from SQLite to Neon (the owner's step)

1. Stop ATIP and the snapshot upload:
   `launchctl bootout gui/$UID/com.atip.platform; launchctl bootout gui/$UID/com.atip.publish-snapshot`
2. Take a copy: `.venv/bin/python -m ops backup` (it is written to `atip_data/backups/`).
3. Put the URL where the LaunchAgent can read it: a line `ATIP_DATABASE_URL=…` in `.env` in
   the project folder, or the URL alone in `atip_data/secrets/ATIP_DATABASE_URL`. Not
   `~/.zshrc`: launchd never reads it, and the scheduled runs would stay on SQLite.
4. Copy the data over the direct URL:
   `.venv/bin/python tools/sqlite_to_postgres.py --source atip_data/backups/<copy>.db` (dry run), then the
   same with `--target '<the direct URL>' --execute`. Every table must report `"ok": true`.
5. In `atip_data/config.json`: `"database": {"backend": "postgresql", "allow_experimental": true}`.
6. `.venv/bin/python main.py --init`. It must print `Database created : PostgreSQL — postgresql://bk_atip_app:***@ep-…`.
7. Start again: `deploy/launchd/install.sh platform` and `deploy/launchd/install.sh snapshot`.
8. Check: `curl -fsS http://127.0.0.1:8000/health/ready`, and the start-up log shows the
   `EXPERIMENTAL PostgreSQL runtime` warning and no `ATIP_DATABASE_URL` error.

To go back, remove the `database` block from `config.json`. ATIP is then on the SQLite file
again, which holds nothing written since the switch.

## Known limits

- **Concurrency.** Writes go through one connection per call, as before. There is no pool in the scheduler yet, so expect SQLite-like concurrency, not more.
- **`date()` comparisons.** The translation compares against a `date`. A column declared `TEXT` that holds dates compares as text in SQLite and fails on PostgreSQL. The route smoke found none, but the write paths of every job have not all been run on PostgreSQL.
- **Rolling back** is switching the three settings back. SQLite stays untouched, but anything written while on PostgreSQL stays there.
